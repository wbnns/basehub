Since the [Denim](/specifications/denim-200ms-blocks/) hardfork, Base no longer previews blocks through Flashblocks. Every 200ms the sequencer produces a full canonical block, and the ordering rules below apply to each one.

## 200ms native blocks

`base-reth-node` builds a complete canonical block every 200ms. Each one carries its own hash, state root, and receipts, and its transactions are sorted by priority fee. The [Denim specification](/specifications/denim-200ms-blocks/) covers the protocol design.

**The pool is frozen at build start.** When the builder begins a block, it takes a snapshot of the transaction pool and fills the block only from that snapshot. Standard transactions and validity transactions follow the same rule. A transaction that reaches the sequencer once a build is under way cannot join that block, however high its priority fee. It becomes eligible for the next block whose build starts after it arrived, and it competes on priority fee there.

**Blocks go out as soon as they are ready.** The sequencer seals a block and broadcasts it the moment the build finishes, instead of waiting for a fixed deadline. Peers therefore see each block earlier and have more of the 200ms window before the next build begins. If the readiness signal never arrives, the sequencer seals at a 150ms deadline. Broadcasting early does not alter a block's contents or timestamps.

<Aside type="note">
Both behaviors went live on Base Mainnet on November 13, 2026. Before that date, only validity transactions used the build-start snapshot.
</Aside>

**Validity transactions** enter the competition for a slot only when all of their predicates match. A matching predicate does not hold any block space for the transaction. See [Validity Transactions](/api-reference/validity-transactions/).

## Mempool visibility

Base does not run a public peer-to-peer mempool. Nodes never gossip pending transactions to each other. A node that is not the sequencer passes what it receives straight on to the sequencer rather than sharing it with peers. Peer-to-peer spread is cut off, but the node you submit to does see your transaction.

That narrows the audience for a pending transaction. It is not front-running or back-running protection:

- **Whoever relays your transaction sees it.** Your RPC provider, wallet, or relayer gets the transaction before the sequencer does, and some of them pass or sell that order flow to searchers.
- **`txpool` methods can expose it.** Any Base node that serves the `txpool` namespace (for example `txpool_content`) will list its pending transactions to whoever can call it. The public `https://mainnet.base.org` and `https://sepolia.base.org` endpoints do not serve that namespace, but other providers and self-hosted nodes are free to turn it on. See [Txpool](/integration-guides/txpool/).
- **Priority fee decides placement.** Anyone who spots your transaction before inclusion can tune the priority fee on their own transaction to land just ahead of or just behind yours.
- **Nothing is encrypted.** The sequencer reads every transaction in the clear and orders it by the rules on this page.

If you want fewer eyes on your pending transactions, send them through an RPC endpoint you trust.

## Flashblocks (retired)

<Aside type="caution">
This section describes the design Base used before [Denim](/specifications/denim-200ms-blocks/). Base stopped producing Flashblocks at Denim activation (Sepolia October 21, 2026; Mainnet November 5, 2026) and turned off the public Flashblocks WebSocket endpoints on November 19, 2026. See [Migrate to 200ms Blocks](/flashblocks/migrate-to-200ms-blocks/).
</Aside>

Blocks were produced by [base-builder](https://github.com/base/base/tree/main/crates/builder), with a fresh priority fee auction held every **200ms**. The auction cut effective block times from 2 seconds to 200 milliseconds via preconfirmations.

<Aside type="note">
For a deeper architectural walkthrough, see the [Flashblocks overview](/flashblocks/overview/).
</Aside>

Three properties set Flashblocks apart from vanilla ordering:

1. **Timing** — The builder emits one Flashblock every 200ms, sealing a slice of the eventual block. Once a Flashblock is broadcast, its ordering is final; later transactions with higher priority fees cannot displace transactions already committed to an earlier Flashblock.

2. **Gas allocation** — Each Flashblock has a progressively larger gas budget. Flashblock 1 may consume up to one tenth of the block gas limit, Flashblock 2 up to two tenths, and so on through Flashblock 10, which may use the full limit.

   | Flashblock | Available gas |
   |------------|---------------|
   | 1 | ~40M gas (1/10) |
   | 2 | ~80M gas (2/10) |
   | 3 | ~120M gas (3/10) |
   | ... | ... |
   | 10 | ~400M gas (full) |

   <Aside type="note">
   In practice, transaction size rarely decides which Flashblock you land in. The [per-transaction gas maximum](#per-transaction-gas-maximum) of 16,777,216 gas (~16.7M) sits below Flashblock 1's ~40M budget, so any valid transaction is already eligible for the first Flashblock. Inclusion timing is driven mainly by priority fee relative to others competing in the same 200ms window.
   </Aside>

3. **Dynamic mempool** — The builder keeps accepting new transactions while a Flashblock is being assembled. This minimizes inclusion latency, but transactions are ordered by fee *at the moment of selection*, not against every transaction that arrived during the 200ms window. A high-fee transaction that arrives late may appear after a lower-fee transaction that was already committed.

   <Aside type="note">
   This is an intentional trade-off — faster inclusion at the cost of occasionally violating strict priority gas auction (PGA) ordering inside a Flashblock. The [Flashblocks FAQ](/flashblocks/faq/) covers the implications in more detail.
   </Aside>

## Per-transaction gas maximum

Since the [Azul hardfork](/specifications/azul-overview/), Base applies a protocol-level ceiling of **16,777,216 gas (2^24)** to any single transaction, as specified by [EIP-7825](https://eips.ethereum.org/EIPS/eip-7825). A transaction that declares a gas limit above this figure is **rejected during block validation**, and `eth_sendTransaction` or `eth_sendRawTransaction` returns a JSON-RPC error — for instance, `exceeds maximum per-transaction gas limit`.

<Aside type="note">
The cap does not apply to deposit transactions. Those are instead bounded by the largest amount of gas that fits in an L1 block, which is 20,000,000 gas.
</Aside>

Operators running bundlers for smart contract wallets need to size each bundle so that it stays within this limit.

## Vanilla ordering

Under the legacy configuration, [op-geth](https://github.com/ethereum-optimism/op-geth) builds a block every 2 seconds and orders transactions inside the block by priority fee. See the [reference implementation](https://github.com/ethereum-optimism/op-geth/blob/optimism/miner/worker.go#L627).

The software that applies these ordering rules is public, from base-builder to the transaction pool. [Reliability and Liveness](/security/reliability-and-liveness/#open-source-sequencer-components) lists each component and links to its repository.
