<Aside type="danger">
Operator releases have moved to [base/base](https://github.com/base/base/releases). Starting at **v1.3.0**, the operator node ships from that repository, and every later release lands there.

`base/node` **becomes read-only on September 4, 2026**. After that date it accepts no issues, no pull requests, and no releases, and it stays online only as a record of the pre-v1.3.0 tags. Point any new install or upgrade at `base/base`.

## Minimum Versions

A Base Mainnet node needs base/base [v1.5.1](https://github.com/base/base/releases/tag/v1.5.1) or newer. A Base Sepolia node needs [v1.5.0](https://github.com/base/base/releases/tag/v1.5.0) or newer. The safest choice on either network is the [latest release](https://github.com/base/base/releases/latest). When you pin a tag with `NODE_TAG`, never pick one below your network's floor.

<Aside type="caution">
**v1.5.4 raised the engine persistence defaults.** The node now holds many more blocks in memory before it flushes them to disk:

| Flag | Before v1.5.4 | v1.5.4 and later |
|------|---------------|------------------|
| `--engine.persistence-threshold` | `7` | `70` |
| `--engine.memory-block-buffer-target` | `5` | `70` |
| `--engine.persistence-backpressure-threshold` | `16` | `160` |

Expect higher memory use, and a longer block replay after a crash or other unclean stop. Give the host more memory, or pass the old values on the command line if you want the previous behavior.
</Aside>

## L1 Beacon Blob Retention

Base publishes its batches to Ethereum as [EIP-4844](https://eips.ethereum.org/EIPS/eip-4844) blobs, and `base-consensus` fetches them from the `BASE_NODE_L1_BEACON` endpoint. A beacon node only has to keep blobs for `MIN_EPOCHS_FOR_BLOB_SIDECARS_REQUESTS` (4,096 epochs, roughly 18 days) and is free to prune anything older. There is no separate blob-archive setting in `base-consensus`. So if your node must derive from L1 data past that window (for example, a snapshot that is more than about 18 days old), the beacon endpoint has to be one that keeps historical blobs.

## Production Images

Production runs are best served by the published Docker image, which is built from [base/base](https://github.com/base/base):

```bash
docker pull ghcr.io/base/node-reth:latest
```

This image bundles both vanilla Reth and Base Reth and can be toggled with the `NODE_TYPE` environment variable:

```bash
# Run Base Reth
docker run ghcr.io/base/node-reth -e NODE_TYPE=base

# Run vanilla Reth
docker run ghcr.io/base/node-reth -e NODE_TYPE=vanilla
```

## Pinning a Release with `NODE_TAG`

The root `docker-compose.yml` in `base/base` pulls `ghcr.io/base/node:latest` unless you say otherwise. To run one specific published release without compiling anything, name its tag:

```bash
NODE_TAG=v1.3.0 docker compose up
```

A pinned tag bypasses the source build completely, so the node starts once the pull finishes. Leave `--build` off when you pin. Passing it triggers a local compile that takes precedence over the tag you asked for.

Note that `v1.3.0` is the earliest release published to `ghcr.io/base/node` out of `base/base`. Tags older than that were never pushed to this image path, so they are not reachable by pin.

### Compose Variables

A handful of variables let you retune the compose file from your shell or a `.env` file, so you never have to edit the file itself:

| Variable | Default | Purpose |
|----------|---------|---------|
| `NODE_TAG` | `latest` | Tag pulled from `ghcr.io/base/node`. Give it a release tag such as `v1.3.0` to pin. |
| `NETWORK_ENV` | `.env.mainnet` | Env file loaded by the `execution` and `node` services. Use `.env.sepolia` for testnet. |
| `HOST_DATA_DIR` | `./reth-data` | Host directory bind-mounted to `/data` in the execution container. Repoint it at an external volume if you need to. |
| `PROFILE` | `release` | Cargo profile applied when you pass `--build`. It matches the profile behind the published image. |

Running `docker compose up --build` compiles whatever is in your `base/base` checkout through the `base` target of `etc/docker/Dockerfile.rust-services`. That is the same target the published `ghcr.io/base/node` image comes from, so a local build and a pinned image lay out their binaries identically.

## Building from Source for Deployment

If you need a custom build:

```bash
# Standard release build
just build release
```

A local `--build` compiles with `release`, which sets `opt-level = 3`, `lto = "thin"`, `codegen-units = 16`, and strips symbols. Note that this is not the profile behind the image you pull. Base bakes its published images with `maxperf`, which adds fat LTO and one codegen unit on top of `release`. Expect a locally built node to behave the same and to benchmark a little slower.

If you need to profile a deployed binary, build the `release-symbols` variant instead. It keeps `release` codegen untouched and only restores the symbol table:

```bash
cargo build --profile release-symbols --package base-reth-node --bin base-reth-node
```

A `release` build leaves the binary at `target/release/base-reth-node`. See [Configuration](/node-operations/configuration/#build-profiles) for the full profile table.

## Hardware Requirements

Base Reth Node requires:

- **CPU:** Multi-core processor (4+ cores recommended)
- **Memory:** 16 GB+ RAM
- **Storage:** NVMe SSD with sufficient space for chain state
- **Network:** Stable, high-bandwidth connection
