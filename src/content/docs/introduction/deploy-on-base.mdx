Set up a Foundry project, point it at Base, and deploy a contract to Base Sepolia in a single end-to-end workflow.

Base is EVM-equivalent, so Solidity and Vyper contracts carry over from Ethereum unchanged — same bytecode, same ABIs, same tooling. The one place that equivalence stops is the precompiles.

Base adds **native precompiles** at fixed addresses — the [B20 token standard](/specifications/b20/), the PolicyRegistry, and the B20 Factory among them. They are built into the node, so those addresses hold no bytecode, and a local EVM that does not know about them reverts the moment a contract calls one.

Stock [Foundry](https://getfoundry.sh/) now handles this. From v1.8.4, `forge`, `cast`, `anvil`, and `chisel` implement Base's precompiles, and from v1.9.0 they also run the [Denim](/specifications/denim-overview/) rules that are live on Base Mainnet and Base Sepolia. Base support is switched on by choosing a Base hardfork, which this guide does below.

<Aside type="caution">
Anything older than Foundry v1.8.4 has no Base precompiles. A contract that touches one, for example by deploying or calling a [B20 token](/specifications/b20/), will fail in local tests and simulations. Check with `forge --version` and upgrade if needed.
</Aside>

Ordinary token standards need none of this. ERC-20, ERC-721, ERC-1155, ERC-4626 vaults, and permissioned designs such as ERC-3643 are plain contracts and deploy on Base exactly as they do on Ethereum. B20 is the exception because it lives in the node: its method and event signatures are part of consensus, they keep parity with the core ERC-20 surface, and any B20 change ships with a network upgrade.

## What you build

By the end of this guide you will have:

- A Foundry v1.9.0+ environment with Base's precompiles enabled
- A smart contract deployed to Base Sepolia
- A connection pattern your frontend can reuse against your contracts

<Aside type="tip">
Base is a fast, low-cost, builder-friendly Ethereum L2 designed to bring the next billion users onchain. Following this guide plugs you into a wide ecosystem of developers, creators, and operators building the global onchain economy.
</Aside>

## Set up your development environment

1. Create a project directory.

```bash
mkdir my-base-project && cd my-base-project
```

2. Install Foundry v1.9.0 or later.

```bash
curl -L https://foundry.paradigm.xyz | bash
foundryup
```

Confirm what you got with `forge --version`. To pin a release, use `foundryup --install <version>`, for example `foundryup --install v1.9.0`.

3. Initialize a Solidity project.

```bash
forge init
```

4. Turn on Base's precompiles for local tests. Add a Base hardfork to the `[profile.default]` section of `foundry.toml`; `base:Denim` matches what Base Mainnet and Base Sepolia run today.

```toml
hardfork = "base:Denim"
```

The project is ready. The starter contract sits at `src/Counter.sol` — this guide uses that contract as the deployment target.

### Choosing where Base is enabled

Foundry behaves like Ethereum unless told otherwise, and the switch differs by context:

| Where it runs | How to enable Base |
|---|---|
| `forge test` and `forge script` locally | Set `hardfork = "base:Denim"` in `foundry.toml`, or pass `--hardfork base:Denim` |
| A local `anvil` node | `anvil --hardfork base:Denim` |
| A fork of Base Mainnet or Base Sepolia | Pass `--fork-url`; Foundry detects Base from the chain ID. Also pass `--hardfork base:Denim` (see below) |
| `cast` against a live Base RPC | Nothing; the Base node executes the precompiles |

<Aside type="caution">
Always name the hardfork. With `--network base` and no `--hardfork`, `forge` falls back to Azul, which has none of the B20 or PolicyRegistry precompiles, so calls into them revert. Foundry v1.9.0's built-in Base schedule also stops at Beryl, which is why a Mainnet fork still needs `--hardfork base:Denim`.
</Aside>

The hardfork value picks which upgrade's rules and precompiles Foundry applies. Match it to the upgrade live on your target network:

| Value | Base precompiles |
|---|---|
| `base:Azul` | None |
| `base:Beryl` | B20 factory, B20 tokens, PolicyRegistry, ActivationRegistry |
| `base:Cobalt` | Beryl's precompiles with Cobalt's B20 changes |
| `base:Denim` | Cobalt's precompiles with Denim's B20 and PolicyRegistry changes (requires Foundry v1.9.0 or later) |

### Coming from base-anvil

[base-anvil](https://github.com/base/base-anvil) is Base's own Foundry fork. It installs prefixed binaries next to stock Foundry, with the precompiles on by default, and earlier versions of this guide used it. New projects should use Foundry v1.9.0 or later instead. Some B20 issuance samples still call `base-cast` (pinned to base-anvil `v1.1.1`); since those hit a live RPC, plain `cast` from v1.8.4 onward runs them unchanged.

| Command | Foundry v1.9.0+ equivalent |
|---|---|
| `base-forge` | `forge` with `hardfork = "base:Denim"` |
| `base-cast` | `cast` |
| `base-anvil` | `anvil --hardfork base:Denim` |
| `base-chisel` | `chisel` |

## Configure the toolchain for Base

Deploying to Base requires two pieces:

1. An RPC connection to the network
2. A funded private key for signing the deployment transaction

### 1. Set up your RPC connection

1. Create a `.env` file at the project root.
2. Add the Base RPC URLs.

```bash
BASE_RPC_URL="https://mainnet.base.org"
BASE_SEPOLIA_RPC_URL="https://sepolia.base.org"
```

3. Load the variables into your shell.

```bash
source .env
```

<Aside type="tip">
Base Sepolia serves as the Base test network, and the rest of this guide runs against it. Free Base Sepolia ETH is available from the [faucets list](/network/network-faucets/).
</Aside>

### 2. Secure your private key

1. Import your private key into the encrypted keystore.

```bash
cast wallet import deployer --interactive
```

2. Paste the key when prompted and set a password.

The encrypted key is stored at `~/.foundry/keystores`, which is excluded from git.

<Aside type="caution">
Never share or commit a private key. Treat it as a credential and store it accordingly.
</Aside>

## Deploy your contract

With the environment configured, deploy to Base Sepolia.

1. (Optional) Run a dry run first to confirm the deployment is well-formed.

```bash
forge create ./src/Counter.sol:Counter --rpc-url $BASE_SEPOLIA_RPC_URL --account deployer
```

This simulates the deploy without broadcasting. You will see the transaction details and ABI; nothing is written onchain.

2. Add `--broadcast` to actually deploy.

```bash
forge create ./src/Counter.sol:Counter --rpc-url $BASE_SEPOLIA_RPC_URL --account deployer --broadcast
```

<Aside type="tip">
The `--broadcast` flag is required to send the transaction. Without it, the run stops at simulation.
</Aside>

The contract argument follows the format `<contract-path>:<contract-name>`.

3. A successful deploy prints output similar to:

```
Deployer: 0x...
Deployed to: 0x...  <-- YOUR CONTRACT ADDRESS
Transaction hash: 0x...
```

4. Save the deployed address into `.env`.

```bash
COUNTER_CONTRACT_ADDRESS="0x..."
```

Replace `0x...` with the address from the output.

5. Reload the variables.

```bash
source .env
```

<Aside type="tip">
Re-run `source .env` after every change to load new variables into the current shell.
</Aside>

### Verify your deployment

To confirm the contract is live:

1. Look up the transaction hash on [Sepolia Basescan](https://sepolia.basescan.org/).
2. Read the contract directly with `cast`:

```bash
cast call $COUNTER_CONTRACT_ADDRESS "number()(uint256)" --rpc-url $BASE_SEPOLIA_RPC_URL
```

<Aside type="tip">
The command requires `COUNTER_CONTRACT_ADDRESS` in `.env` and a fresh `source .env`. Otherwise the variable expands to nothing and the call fails.
</Aside>

The call returns the initial value of the Counter's `number` storage slot, which is `0`.

The contract is now live on Base Sepolia.
